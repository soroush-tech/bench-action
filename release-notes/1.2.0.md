## bench-action@1.2.0

The PR comment now leads with one summary table across every bench file, so a run that
covers many files reads at a glance: what failed, and how far each case is from the
baseline (soroush-tech/core#355). Each file's full table is still there, folded underneath.
Existing workflows need no change, and the comment they already have is updated in place.

### Features

- **Summary table.** One row per case that is not the baseline, from every file: status,
  case, file, speed vs the baseline (the number `min-ratio` gates on) and mean time. Failures
  come first, then the rest from slowest to fastest. A bench comparing three or more packages
  gets one row per package. A file that produced no results, or failed without any case below
  the minimum (e.g. a case crashed), still gets a row, so a failure is never missing.
- **`comment-details`** (`collapsed` by default): each file's own table sits in a closed
  `<details>` under the summary. `open` shows them expanded; `none` posts the summary only.
- **`comment-title`** (`Benchmark results` by default): the comment heading. Any other title
  gives the comment its own marker, so two bench jobs on one PR (e.g. Node and browser
  benches) keep separate comments instead of overwriting each other.
- If the per-file tables would push the comment past GitHub's size limit, they are left out
  with a note, and the summary is still posted.

### Internal

- Re-vendors `@soroush.tech/bench` **2.3.0**: each file's run also writes `--json-file`, and
  the summary is built from those raw numbers (soroush-tech/core#356).
- The sticky comment is matched by its first line (the marker), the same rule the bench relay
  uses (soroush-tech/core#358). Until the relay with that rule is deployed, a comment with a
  custom title falls back to `github-token`.
